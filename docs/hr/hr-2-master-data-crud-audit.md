# EFFITRANS-HR-2 — master data & employee registry CRUD audit

**Date:** 2026-08-14 · **Baseline:** `c110379` (CI #468 GREEN) · **Audit only — nothing implemented, granted, activated or mutated.**

## The one-line answer

**The registry is complete, the master data is create-only, and the import
pipeline is real but shallow and endless** — it exists for employees (CSV,
mapping, validation, four-eyes), but it cannot read Excel, offers no template,
validates only four things, and by design never applies. The platform can
already be built up gradually by hand; the accelerator needs one master-data
phase (small) and one import-completion phase (the real build).

Duplicate prevention is real at the database: `unique (tenant, code)` on units,
`(tenant, title)` on positions, `(tenant, name)` on sites, and one open PRIMARY
assignment per employee. Tenant isolation holds throughout (all writes via the
guarded actions; HR-A2 established the actions ARE the boundary).

**The master-data gap in one sentence: everything can be created and nothing can
be corrected.** A typo in a unit name, a renamed position, a moved site — all
currently require creating a second record and abandoning the first. For a
platform meant to be the system of record, Update is not optional. Deactivation
also performs **no referential check** — a unit with active placements can be
deactivated silently (existing assignments survive; only *new* assignments are
refused by `validateAssignmentTargets`). Acceptable, but it should warn.

## 2. Employee registry — class A, with the rules intact

`createEmployee` → `updateEmployee` → `transitionEmployee` (DRAFT → ACTIVE →
SUSPENDED → TERMINATED; rehire = new record, DEC-B26) → `linkEmployeeAccount` /
`unlink` → `setEmployeeAssignment` (unit/position/site/manager, tenant-validated,
effective-dated) → documents + contracts (four-eyes verification).

* **Employee ≠ application user** holds; the link grants nothing (proven live).
* **Matricule is system-controlled and immutable**: generated by
  `next_employee_number` at creation; `updateEmployee` cannot touch
  `employee_number` (verified — the update path never references it). The
  HR-0R immutability concern is closed in practice.
* ⚠ **One coherence note**: the manager exists TWICE — `employee.manager_employee_id`
  (HR-1, migration comment: *display-only, grants no access*) and
  `employee_assignment.manager_employee_id` (HR-A2, effective-dated). HR-B1's
  scoped-approval design reads the **assignment's** — the authoritative one.
  The duplicate is tolerable today (0 rows) but the import and HR-B1 must agree
  on which they write, or the two will drift from row one.

**§6 answered precisely:** prepare ✅ · validate ✅ · submit ✅ — all possible
today with one officer. Approve ❌ until the second HR_OFFICER exists
(`same_actor`). Apply ❌ until built. So HR can accumulate fully-validated,
submitted batches now, and nothing reaches production until both the second
officer and HR-B3 exist. The control survives activation untouched.

## 4. Template and validation — schema-derived, and both too thin

**Current EMPLOYEES template** (from `KIND_FIELDS`, the code's own contract):
required `first_name`, `last_name`, `department`; optional `employee_number`,
`job_title`, `email`, `phone`, `status`, `hire_date`.

**Against the employee schema and the business list, missing from the template:**
`employment_type` (CDI/CDD/…), **position** (reference), **work site**
(reference), **manager** (reference), `professional_phone` vs `personal_phone`
distinction, probation date. And **`employee_number` should leave the template's
default path**: matricules are system-minted; a supplied number belongs only to
an explicit ratified legacy lane, exactly as the FIN-AGING legacy import
distinguishes provenance.

**Current validation checks exactly four things**: required fields present ·
`department` ∈ the canonical 4 · `status` ∈ vocabulary · date parses. **Absent
(verified — no such code exists):** duplicate against production · duplicate
within the file · duplicate e-mail · manager resolution · position/site
resolution (their columns don't exist yet) · employment-type check.
None of this is a defect today — the columns it would validate aren't in the
template — but it is the exact work list for the import-completion phase.

**Classes:** existing pipeline **A** for its scope · template **C** ·
validation depth **C** · xlsx **D** (needs a parser dependency — flag: CSV
already satisfies « Excel and/or CSV »; Excel-native is an enhancement decision)
· template download **D** · apply stage **D** (defined by HRQ-A4 = YES) ·
report **D**.

## 5. Gradual construction (§7) — confirmed

Manual-first works end to end today: configuration → units → positions → sites →
`createEmployee` (unit optional, prefix defaults) → assignment → link. **Bulk
import is an accelerator, not a prerequisite** — nothing in the manual path
touches the import pipeline. HR-B0 is unchanged and still first.

## 6. Manager relationships (§8) — sufficient for HR-B1/B2

`employee → manager` = `employee_assignment.manager_employee_id` (current
placement) · `employee → unit` = `employee_assignment.org_unit_id` · unit
hierarchy = `hr_org_unit.parent_id` with kind-ordered CHECK. That is enough for
the ratified scoped-authority designs. What does **not** exist — a *manager of a
department* — HR-1A already established should not be invented.

## 7. Engineering gaps (exact), configuration gaps, and phases

**HR-C1 — master-data completion (small, no dependencies):**
`updateOrgUnit` (rename/re-parent with hierarchy re-check) · `updatePosition` ·
`updateWorkLocation` · `setPositionActive` · `setWorkLocationActive` ·
referential warning on unit deactivation. All follow existing action patterns;
no migration expected (columns exist: `is_active` on units — positions/sites
need an active flag check → may need **one** small migration if absent; verify
at implementation).

**HR-B3 — import completion (the required build):**
template download (CSV first) · extended EMPLOYEES columns (employment_type,
position/site/manager by reference) · deep validation (production duplicates,
in-file duplicates, e-mail, reference resolution) · the **apply stage** —
consuming matricules through `next_employee_number`, validating placements
through `validateAssignmentTargets`, writing through the same rules as
`createEmployee`, never a parallel path · import report. xlsx behind a separate
decision.

**Configuration/data gaps:** unchanged from HR-1 — the HR-B0 session, the
employees themselves, the second officer.

**Dependency order:** HR-B0 (operator) → 2nd officer → **HR-C1** → **HR-B3** →
HR-B1 → HR-B2 → HR-8 → HR-9 → HR-7.
(HR-B1/B2 stay behind their two Effitrans confirmations from HR-1A.)

## 8. UAT plan (post-HR-C1/B3, incremental)

1. Rename a unit; move a section under another department; deactivate an unused
   position — verify history preserved, no employee orphaned.
2. Download the template · fill 5 real rows · upload · verify « 5 lignes · N
   valides · M à corriger » with row reasons · fix file · re-upload.
3. Submit as officer 1 · verify approve refused for officer 1 (`same_actor`) ·
   approve as officer 2 · apply · verify matricules EMP-NNNN continue the manual
   sequence · import report lists created employees.
4. Verify a supplied `employee_number` in the file is refused (or accepted only
   through the explicit legacy lane, whichever HR-B3 ratifies).

## 9. The smallest next phase

**HR-C1.** It is the smallest coherent slice (five actions + one warning, in an
established pattern), it has zero pending business input, and it makes the
system-of-record claim true for the data every other phase builds on. HR-B3 is
the priority *build*; HR-C1 is the right *next step*.
